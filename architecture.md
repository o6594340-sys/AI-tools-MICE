# Архитектура: Мульти-DMC сборщик сметы

Дополняет [brief_another.md](brief_another.md). Версия после критики 6 независимых технических экспертиз — исходный вариант был спроектирован "как функция", здесь исправлено на "как систему".

---

## Модель исполнения — job-based, не синхронная сессия

Каждая загрузка создаёт `smeta_job_id`. Все промежуточные артефакты (сырые прайсы, нормализованные LineItem/ProgramItem, кандидаты матчинга, подтверждённые маппинги) пишутся на диск/в SQLite под этим id — **не во Flask-сессию** (не выдержит объём: эмбеддинги + списки позиций по 5+ прайсам).

Каждый прайс — независимая подзадача со статусом `pending / extracted / matched / failed`. Если LLM падает на 3-м из 5 прайсов — остальные не блокируются, экран подтверждения показывает "4 из 5 готовы, retry для #3".

Между модулями (extract/match/assemble/render) — версионированный контракт: `schema_version` в каждом JSON-артефакте, репозиторий-слой вместо прямого импорта внутренних структур друг у друга.

## Приватность — честная формулировка, не маркетинговая

"Нулевое хранение" описывает только сервер приложения, не весь путь данных — прайсы всё равно уходят в Anthropic API для матчинга. Явно оговорить:
- ZDR (Zero Data Retention) соглашение с провайдером API, если доступно
- TTL-очистка temp-файлов по cron **независимо от happy path** (не полагаться только на "удалить после экспорта" — прерванная сессия иначе оставляет файл навсегда)
- **Анонимизация до отправки в LLM**, не только в UI: placeholder-токены вместо реальных названий DMC в промпте, реальные имена подставляются обратно только на экспорте у клиента. UI-маскировка "Поставщик А/Б/В" без этого — косметика, не приватность (реальное имя уже прошло через API-логи/трейсы).

## Матчинг

Двухступенчатый (эмбеддинги для отбора кандидатов + LLM-верификация), с тремя поправками:

1. **Бандлы/пакетные цены** — отдельный этап группировки ДО парной верификации (определить кластеры "позиции программы → один объект прайса" на уровне каждого прайса), расщепление цены бандла — явно помеченная оценка, обязательно уходит на подтверждение человеком с предупреждением, не auto-fill.
2. **Confidence некалиброван по умолчанию** — используется только как UX-сигнал для приоритезации ручной проверки, не как гарантия точности. Единственная программно верифицируемая проверка — что цитата является реальной подстрокой исходного прайса (можно проверить кодом на 100%).
3. **Батчинг по позиции программы**, не по паре: один вызов на позицию программы со всеми топ-3 кандидатами сразу (~35 вызовов на смету вместо 105), параллельно с ограничением конкурентности (~10-15), с потоковым выводом прогресса на фронт по мере готовности каждой позиции.

## Excel-рендеринг — новый подход по умолчанию

Статичный маппинг "ячейка = категория" ломается на реальных шаблонах: число дней/сессий меняется, вставка строк не сдвигает формулы/merge/условное форматирование автоматически. openpyxl дополнительно теряет диаграммы, VBA-связи, сложное условное форматирование при перезаписи.

**По умолчанию:** не писать в оригинальный файл агентства. Экспорт в чистый промежуточный формат (JSON/CSV с суммами по категориям) + отдельный простой Excel-отчёт, который агентство переносит в свой шаблон вручную.

**Опционально** (для узкого класса простых шаблонов без VBA и сложного merge): прямая запись через маппинг "шаблонных блоков с правилами повторения" (per-day/per-session блок + якоря вроде "Итого"/название категории), не фиксированных координат ячеек. Обязательна проверка version fingerprint (хэш структуры листов+ключевых ячеек) при каждом использовании — при расхождении блокировать автогенерацию и требовать повторный прогон онбординга, а не тихо писать в потенциально мёртвые ссылки.

## Стоимость и производительность

- Экстракция: ~6 вызовов (5 прайсов + программа), пренебрежимо дёшево
- Верификация: ~35 батчированных вызовов (не 105 попарных), параллельно → **реалистично 30-60 сек** с потоковым прогрессом вместо 3-5 минут при последовательной обработке
- Стоимость на смету: **~5-10₽** с prompt caching, несущественно относительно бюджетов MICE-программ
- Оптимизации: кэш эмбеддингов прайсов между сессиями (DMC часто присылают один и тот же прайс повторно), prompt caching системного промпта верификации, гибридная маршрутизация (Haiku для явных совпадений с embedding-score >0.9, Sonnet только для неоднозначных)
- **Риск:** 3-минутное ожидание на живом стенде выставки убьёт демо сильнее любой неточности матчинга — параллельно-потоковый пайплайн нужно закладывать сразу, переделывать архитектуру вызовов после того, как UI завязан на синхронный ответ, дороже.

## MVP для демо на воркшопе (что реально упростить)

**Упростить/захардкодить:**
- 1-2 захардкоженных шаблона агентства вместо мастера онбординга
- Одна стратегия сборки (мин. цена), остальные — кнопки-заглушки "скоро"
- Один проход LLM со structured output вместо двухступенчатого эмбеддинг-матчинга
- Файловое хранилище вместо БД
- Константы "Поставщик A/Б/В" вместо полноценной анонимизации
- Счётчик экономии — эвристический расчёт постфактум, не отдельная аналитика

**Не упрощать (ядро ценности):**
- Экстракция прайсов в каноническую схему — без этого нет данных для сборки
- Экран подтверждения человеком — без него демо выглядит "чёрным ящиком" и не вызывает доверия к денежному документу
- Вывод в Excel-подобном виде — то, что агентство реально уносит со стенда

## Пересмотренный план фаз

1. **MVP** (job-модель на файлах, один проход матчинга, один захардкоженный шаблон, одна стратегия, параллельно-потоковая обработка) — для демо на воркшопе
2. **Мастер онбординга шаблона + калибровка confidence на реальных данных пилотных агентств** — после подтверждения спроса
3. **Персистентность профилей, биллинг, полноценная анонимизация, ZDR-договор с провайдером** — только при появлении платящих клиентов
