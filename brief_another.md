# Бриф: Мульти-DMC сборщик сметы

Продукт-кандидат №4 в линейке студии (наряду с конструктором мобильных приложений, генератором презентаций и MICE Draft). Готовился для воркшопа, где пользователь — экспонент, целевая аудитория — MICE-агентства и корпоративные клиенты MICE-проектов.

---

## Проблема

MICE-менеджер получает несколько прайсов/предложений от разных DMC-поставщиков на один тендер. Каждый DMC оформляет прайс по-своему (формат, язык, формулировки услуг, пакетные цены). Сведение этих прайсов в одну смету под финальную программу для клиента делается вручную — часы работы на один тендер, риск ошибок, риск пропустить более дешёвый вариант по конкретной позиции.

Более ранняя идея — калькулятор сметы на основе рыночных бенчмарков (Booking.com и т.п.) — отклонена: нет источника достоверных данных по большинству категорий (трансферы, экскурсии, банкеты, DMC-услуги нигде не публикуются), розничные цены отелей не совпадают с групповыми ставками, ручная курация и учёт сезонности/блэкаутов пользователем признаны нереалистичными.

## Целевая аудитория

MICE-агентства, в первую очередь те, что ведут несколько параллельных тендеров с 2+ DMC-поставщиками на регулярной основе (сегмент с высокой частотой, не разовые пользователи — см. риски ниже).

## Как это работает

**Вход:**
1. Несколько прайсов/КП от разных DMC на один тендер (PDF/Excel/Word, разный формат и формулировки)
2. Финальная программа/маршрут, который агентство хочет показать клиенту
3. Собственный Excel-шаблон сметы агентства (у каждого свой)

**Логика:** система сопоставляет каждую позицию финальной программы с эквивалентными позициями во всех загруженных прайсах и заполняет смету агентства по выбранной стратегии:

- **Минимальная цена по всем DMC** — по каждой позиции берётся самая низкая цена среди поставщиков, у которых она есть. Агентство может использовать эти цифры, чтобы дожать по цене выбранного основного поставщика (не обязательно реально заключать договор с каждым — это уже вне ответственности инструмента).
- **Один поставщик целиком** — вся смета строится на прайсе одного DMC.
- **Микс по категориям** — например, отели и логистика от одного DMC, уникальная "креативная"/эксклюзивная часть программы — от другого. Категории и их источник назначает пользователь.

**Обработка пробелов:** если позиция есть только у одного DMC — берётся его цена. Если позиции нет ни у одного DMC — строка остаётся в смете (описание услуги + формула на месте), цена = 0 — для ручного дозаполнения, а не выпадает из документа.

**Ключевое отличие от предыдущей версии идеи:** не требует никаких внешних рыночных данных — все цифры дают сами пользователи (их собственные прайсы от их собственных поставщиков). Проблема "откуда брать актуальные цены" снимается архитектурой, а не решается.

---

## Обязательные архитектурные требования (по итогам оценки, см. ниже)

1. **Human-in-the-loop обязателен, не опционален.** Полный автопилот ненадёжен для денежного документа: пакетные цены, скрытые включения ("обед включён" внутри строки экскурсии), разная гранулярность позиций между DMC — LLM предлагает сопоставления с confidence-score и цитатой исходной строки прайса, менеджер подтверждает/правит до финальной сборки. Спорные/неуверенные сопоставления — в отдельную очередь, не автозаполняются молча.
2. **UX как матрица "категория × поставщик"**, а не построчный список из 30+ позиций: укрупнённые категории (Отели / Логистика / Экскурсии / Креатив), назначение категории поставщику одним действием (не дропдаун на каждую строку), точечный override отдельной позиции при необходимости.
3. **Прозрачность источника цены прямо в смете** — бейдж/пометка, у какого DMC взята каждая цена, сохраняется при экспорте (нужно знать, кому звонить бронировать; критично для доверия).
4. **Разовый "мастер онбординга" шаблона агентства** вместо попытки распознавать любой Excel-формат "из коробки": пользователь один раз загружает образец сметы, система предлагает маппинг ячеек/структуры, человек подтверждает. Без этого продукт превращается в скрытую индивидуальную разработку под каждого клиента.
5. **Анонимизация поставщиков в выводе по умолчанию** (Поставщик А/Б/В) — снижает риск случайного раскрытия чужих цен, например при демонстрации экрана клиенту.
6. **Нулевое хранение / локальная обработка** с понятной формулировкой для агентства (не просто пункт в EULA) — иначе агентства не понесут в инструмент реальные прайсы своих DMC-партнёров.
7. **Счётчик экономии в интерфейсе**: "сведено N позиций из M прайсов за X минут, сэкономлено ≈Y часов / Z рублей" — прямой аргумент ценности, показывается сразу после сборки.

## Монетизация

Оплата "за смету" / пакет смет — понятнее подписки при нерегулярном использовании (агентства платят по факту тендера). Возможна гибридная модель: разовая оплата + подписка с лимитом тендеров/мес для агентств с постоянным потоком. Ценность считается напрямую в часах ручной сверки (обычно 3–8 часов на тендер при 4–6 DMC) и в марже за счёт неупущенных дешёвых позиций.

## Ключевые риски

- **Структурное ограничение массовости:** большинство MICE-агентств в СНГ ведут 1–3 тендера в квартал с 2–3 DMC — им проще свести вручную в Excel за 20 минут. Инструмент реально ценен для агентств с высоким потоком мультитендеров (премиум-сегмент, не флагманский продукт для каждого посетителя стенда).
- **Технический:** тихие ложноположительные сопоставления похожих, но не идентичных услуг (трансфер А↔Б, тур 3ч↔4ч) в денежном документе без сигнала об ошибке — критично при отсутствии human-in-the-loop.
- **Масштабируемость:** запись в уникальный шаблон агентства (мёрдж-ячейки, формулы, скрытые листы) — это не задача "распознать любой формат", а задача понять чужую финансовую модель; без разового онбординга рискует превратиться в скрытую bespoke-разработку под каждого клиента.
- **Отношения с поставщиками:** если у студии появятся партнёрства с DMC в будущем, инструмент, чья явная цель — "дожимать поставщика по цене, сравнивая с конкурентами", DMC могут воспринять как враждебный даже при нулевом хранении данных.
- **Демо на стенде:** продукт про закулисную рутину, а не яркий генеративный вывод — случайный посетитель без своего тендера в руках может не считать боль за 20 секунд без заранее подготовленного демо-кейса (несколько "брендированных" фейковых прайсов под понятную программу + живое переключение стратегии с анимированным пересчётом экономии).

## Открытые вопросы

- Уточнить референс "конструкторы предложений для Дубая и Японии" — упомянут пользователем как что-то похожее, сделанное ранее, но не найден в текущем репозитории.
- Определить приоритет: делать ли это как отдельный продукт №4 или как premium-режим внутри MICE Draft (общая инфраструктура парсинга файлов уже есть).
- Решить модель разграничения "разовая оплата vs подписка" до начала разработки MVP.
